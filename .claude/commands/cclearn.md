用户会告诉你一条从 code review、调试或开发中学到的规则或教训。

## 你的任务

1. **理解规则本质**：提炼用户描述的核心要点，不要照搬原话，要抽象为可复用的规则
2. **检查去重**：读取项目根目录的 `CLAUDE.md`，确认没有已存在的重复或矛盾规则
3. **追加规则**：将新规则追加到 `CLAUDE.md` 中合适的章节
4. **如果没有合适的章节**：在合适的位置创建新章节

## 规则格式

```
- **[场景/条件]**：具体做法。原因：为什么这样做。
```

示例：
- **[并发共享资源]**：优先用乐观锁+重试，而非悲观锁。原因：业务读多写少，悲观锁成为瓶颈。
- **[SQL JOIN]**：大表 JOIN 时必须在 ON 条件中包含分区键。原因：避免全表扫描。
- **[ETL INSERT]**：所有 INSERT 语句必须带 ON DUPLICATE KEY UPDATE。原因：不能假设源数据无重复。

## 规则质量要求

- 具体可操作，不说"注意 XXX"这种空话
- 包含"什么场景下"+"怎么做"+"为什么"三要素
- 如果用户描述不完整，追问缺失的部分再写入

## 写入后

- 告知用户已追加的规则内容和所在章节
- 如果发现用户描述的规则和已有规则有关联或冲突，主动指出
